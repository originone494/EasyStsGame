## 一、开发目标与总体策略

根据你提供的策划案和已完成功能，项目目前已经具备一个可以实际操作、可以完成胜负结算的单场战斗原型。

下一阶段的重点不应该是重新制作战场、卡牌拖拽、基础怪物或界面，而是以现有战斗系统为基础，逐步实现完整的 Roguelike 游戏循环。

第一层

10场战斗

第三层

5场战斗

交替穿插商店、火堆、事件，按线性地图推进

第一、二层通关奖励及招募；第三层通关即结束

V15.7 规定全局3层、22场战斗，其中19场非Boss战、3场Boss战；路线固定线性，但特殊节点随机穿插。

## 第一阶段：巩固战斗内核

这一阶段最重要，因为天气、遗物、角色技能、Boss和奖励系统都将依赖战斗底层。必须先解决事件、伤害、同步效果的执行问题。

### 步骤1：整理现有代码，建立统一数据模型

目标： 后续增加角色、卡牌、遗物和战斗内容时，不需要反复修改核心战斗代码。

具体开发任务

1. 备份当前可正常运行的版本，建立独立开发分支。
2. 保留已经验证的22项规则测试、23项浏览器检查和12项启动器测试。
3. 检查现有规则、内容配置、界面三层之间的调用关系。
4. 统一战斗状态、牌组、怪物、角色和事件的数据格式。
5. 给每一张实际卡牌分配独立实例ID，以支持同名复制品独立升级。
6. 将当前13格战场、20生命值和三种测试敌人的数据移入配置层，避免写死在引擎中。

建议采用如下逻辑结构，具体文件位置按现有项目调整：

这是一份推荐的职责划分，不是要求你更换当前技术框架或重建项目目录。

特别需要区分三个概念：

- `CardDefinition`：卡牌类型、效果、基础数值等静态配置。
- `CardInstance`：某一张实际持有的卡，记录实例ID、升级状态等。
- `BattleCardState`：卡牌在当前战斗中的牌区位置及临时状态。

这样才能正确实现每张卡最多升级一次、同名卡独立升级、永久删卡与战斗消耗恢复。

验收标准： 现有全部测试通过，三种战斗布局不变，玩家仍能完成所有现有操作。只改变内部组织，不改变玩法。

### 步骤2：实现完整事件队列与触发系统

优先级：最高

这是整个后续开发最重要的底层功能。

目前的直接效果（攻击、移动、抽牌、击退）已经能执行，但V15.7还要求能够将“直接执行”和“发生事件后的触发”分开。

#### 2.1 建立事件队列

建议定义以下基础事件：

| 事件                | 发生条件          |
| ----------------- | ------------- |
| `CARD_PLAYED`     | 卡牌合法打出        |
| `DAMAGE_RESOLVED` | 完成一次伤害结算，含0伤害 |
| `HP_LOST`         | 实际生命值减少       |
| `ENEMY_DIED`      | 非Boss怪物死亡     |
| `ENEMY_CONTACT`   | 怪物合法接触队伍      |
| `COLLISION`       | 怪物发生实际碰撞      |
| `UNIT_MOVED`      | 单位位置变化        |
| `CARD_DRAWN`      | 抽入卡牌          |
| `CARD_EXHAUSTED`  | 卡牌进入消耗区       |
| `TURN_STARTED`    | 玩家新回合开始       |

这些是建议使用的程序事件名，具体是否需要拆分或合并，可随现有代码结构调整。

例如，玩家使用一张卡牌：

> 造成4点伤害，然后恢复2点生命。

执行顺序应当是：

1. 执行伤害动作，立即改变怪物生命。
2. 记录伤害事件；如果确实扣除生命，再记录生命减少事件。
3. 如果怪物死亡，记录死亡事件。
4. 执行当前卡牌的治疗动作。
5. 当前卡牌直接效果结束，才开始处理积累的事件队列。
6. 遗物或其他监听效果按顺序响应。

如果步骤1已经使玩家死亡，则必须立即失败，不能继续执行后续动作。

#### 2.2 实现统一的触发监听器

每个遗物和具有临时监听能力的效果，应有独立的触发定义。

建议配置字段：

```
{
  id: "relic_example",
  listensTo: ["ENEMY_DIED"],
  condition: "...",
  effects: [...],
  triggerLimit: "unlimited",
  allowChain: true
}
```

这里只展示数据结构，不代表策划案已经确定这件遗物的实际效果。

监听器必须能够处理：

- 监听生效与失效。
- 按登记时间排序。
- 每回合或每战斗的次数限制。
- 遗物获取顺序。
- 事件响应产生后续事件。
- 目标死亡时跳过失效动作，但保留独立动作。
- 遗物在事件出队时统一锁定触发资格和非目标数值。
- 实际执行时再为自动目标效果选择目标。

不能为了简化程序，把所有遗物触发改成“任何伤害发生时立即执行”，否则会破坏大量正式规则。

#### 2.3 完善胜负中断

实现明确的战斗状态，例如：

`PLAYER_TURN → CARD_RESOLVING → EVENT_RESOLVING → ENEMY_TURN → BATTLE_FINISHED`

另设最后击杀收尾状态，区分以下情况：

- 玩家生命归零： 立即失败。
- 非Boss最后怪物被击杀： 完成当前卡牌剩余合法直接效果及相关触发链，再胜利。
- 非Boss最后怪物接触消失： 玩家存活则立即结束。
- Boss接触： 立即终止，按累计伤害是否达标判定。

验收用例：

| 测试                     | 预期        |
| ---------------------- | --------- |
| 最后一击后还有治疗              | 治疗正常执行    |
| 最后一击触发击杀遗物             | 遗物正常响应    |
| 卡牌生命代价致死               | 后续治疗不执行   |
| 同一事件触发两个遗物             | 按登记顺序执行   |
| 前一遗物治疗，后一遗物读取锁定的已损生命数值 | 使用出队时的锁定值 |
| 触发器产生新事件               | 新事件放到队尾   |

完成此步骤后，应新增专门的事件日志和事件回放测试。

### 步骤3：完善伤害公式、生命减少和群体伤害

目标： 让后续不同天气、遗物、卡牌都能复用同一套伤害计算规则。

#### 3.1 统一伤害计算入口

使用策划案明确的公式：

\\[ D=\max(0,\lceil(B+F)\times M_1\times M_2\times\cdots\times M_n\rceil) \\]

其中百分比倍率独立相乘，只在最后向上取整一次。

例如10点基础伤害，受到20%和30%两项独立增伤：

\\[ \lceil10\times1.2\times1.3\rceil=16 \\]

开发上需要区分：

- 卡牌直接伤害。
- 遗物伤害。
- 碰撞等间接伤害。
- 非伤害型的直接生命损失。
- 实际减少的生命值。

0伤害仍然能够记录伤害事件，但不能生成实际生命减少事件。

#### 3.2 增加群体伤害执行器

建议实现：

```
确定本次合法目标集合
       ↓
对各目标独立计算伤害
       ↓
形成同一批次结算
       ↓
同步更新全部目标生命
       ↓
统一判定本批死亡
       ↓
按规则生成伤害、生命减少、死亡事件
       ↓
执行后续动作或处理胜负
```

群体伤害不得直接复用“遍历怪物逐只执行单体攻击”的方式。

这点非常关键，因为多只怪物同步死亡时，遗物事件与评分必须保持一致。

验收标准： 基础10伤害乘1.2和1.3得到16；3段伤害各自计算与取整；0伤害和直接生命损失的事件分类正确；群体伤害同步生效。

### 步骤4：扩展同步击退和复杂碰撞

现有逐格击退、单体传递和边界停止可以保留。

新增部分主要是多目标同时击退。

开发任务：

1. 增加群体击退动作类型。
2. 在执行开始时锁定所有受影响目标。
3. 维护各目标的位置、方向及剩余击退量。
4. 同方向碰撞时传递未消耗的位移量。
5. 处理被撞目标自身已有剩余击退量的累加。
6. 对同步碰撞按位置从左到右入队。
7. 边界消除剩余位移，不允许怪物出界或重叠。
8. 明确反向击退碰撞时的具体处理。

实现注意： 策划案尚未完全确定反向冲突、多重同步冲突和同位置碰撞次级排序。应当先写出独立执行规格，再开发通用求解器，而不是把某一个临时算法当作已确认玩法。

验收标准： 单体击退原有测试通过；多个目标同步移动的结果不取决于数组遍历顺序；任何时刻都不存在最终重叠位置，也不会凭空产生额外击退量。

## 第二阶段：完成战斗规则

### 步骤5：加入天气和适应属性

天气系统可以在现有战斗场景中直接实现，不需要等待地图开发。

#### 5.1 天气规则

共有三种天气：

晴

晴适应生效

雨

雨适应生效

风

风适应生效

每场战斗随机初始天气，随后按照固定顺序：

晴 → 雨 → 风 → 晴

每种天气持续3个完整回合，第4、7、10……个玩家回合开始时切换。

天气更新必须发生在回合开始效果与补手牌之前。

#### 5.2 属性系统

建立三项独立属性：

```
sunAdaptation
rainAdaptation
windAdaptation
```

当前天气对应的每1点属性提供1%卡牌直接伤害加成。

例如晴适应为40点，晴天使用基础10伤害的卡，且无其他修正：

\\[ \lceil10\times1.4\rceil=14 \\]

注意：遗物和碰撞间接伤害不自动享受这一加成。

#### 5.3 界面开发

在现有像素战斗界面增加一个天气信息组件：

- 当前天气图标。
- 当前天气名称。
- 距离下一次自然切换还有几个完整回合。
- 当前生效适应属性与伤害加成。

建议复用已有浮字系统，在天气切换时显示简短提示。

验收标准： 第4、7、10回合正确切换；天气改变后仅对应的卡牌直接伤害发生变化；额外倍率正常独立相乘。

### 步骤6：实现非Boss战斗评分及奖励计算

这是使普通战斗具备“打得好与打得差”的差异的关键系统。

#### 6.1 评分记录

不要只在战斗结束时统计仍留在场上的怪物。

每个怪物都要保留本场评分记录，包括已经死亡或接触消失的怪物。

暂定公式：

\\[ 评分=\frac{怪物实际有效生命损失总和}{本场怪物最大生命总和}\times100\\% \\]

结果限制在0%～100%。

例如两只怪物，每只10生命：

- 第一只击杀，贡献10点生命损失。
- 第二只只造成5点伤害，随后接触消失。
- 总评分为15÷20＝75%。

不能把接触消失当成击杀，也不能让过量伤害提高评分。

#### 6.2 奖励计算

非Boss战斗采用20%保底线性奖励：

\\[ 奖励比例=0.2+0.8\times评分比例 \\]

\\[ 实际奖励=\lceil 基准奖励\times奖励比例\rceil \\]

非Boss战评分与奖励比例

0%评分获得20%基准奖励，100%评分获得100%基准奖励

0%25%50%75%100%0255075100

系统需要分别计算金币和各项适应属性，属性奖励最后还要受当前楼层属性上限限制。

验收标准： 0%评分仍然获得20%基准奖励；50%评分得到60%；100%评分获得满额；角色卡奖励不受评分影响。

### 步骤7：实现Boss输出挑战

这是现有战斗系统中机制差异最大的一部分，应该作为一个独立功能完成，而不是简单增加高血量怪物。

#### 7.1 Boss与普通敌人的差异

| 规则       | 普通敌人     | Boss         |
| -------- | -------- | ------------ |
| 生命降至0    | 死亡并消失    | 不因达到伤害基准而死亡  |
| 达到100%伤害 | 可能被击杀    | 继续战斗         |
| 实际接触玩家   | 造成伤害并消失  | 立即结束战斗       |
| 接触时判定    | 玩家生命是否归零 | 累计伤害是否达到100% |
| 伤害超过生命基准 | 不计多余评分   | 继续累计         |
| 击退       | 正常执行     | 正常执行         |

#### 7.2 新增Boss累计伤害记录

建议数据：

```
bossState = {
  baseMaxHP: 100,
  accumulatedDamage: 0,
  hasContactedPlayer: false
}
```

其中100仅为测试示例，不是正式Boss生命配置。

每次对Boss造成有效伤害时，将伤害完整加入累计记录，不受剩余生命限制。

Boss接触时：

- 累计99%：失败。
- 累计100%：成功。
- 累计110%：成功，评分110%。
- 累计600%：成功，显示600%，但奖励倍率最多500%。

第一、二层成功奖励公式：

\\[ 奖励=\lceil 基准奖励\times\min(伤害比例,5)\rceil \\]

第三层Boss成功后直接通关，不发放任何奖励。

#### 7.3 开发测试局面

增加至少五个独立Boss测试布局：

| 测试局面            | 目的            |
| --------------- | ------------- |
| Boss即将接触，累计99%  | 验证失败          |
| Boss即将接触，累计100% | 验证成功          |
| Boss已累计110%但未接触 | 验证战斗继续        |
| Boss被击退2格       | 验证延迟接触        |
| Boss和小怪同时在场     | 验证小怪消失不导致提前结束 |

验收标准： Boss从不因达到100%伤害自行死亡；首次接触时立即终止；第一、二层正确计算奖励，第三层不产生奖励页面。

## 第三阶段：建立完整 Roguelike 单局

这一阶段的目标是：让玩家从一场战斗打到下一场战斗，并能获得持续成长。

### 步骤8：实现楼层与线性地图

#### 8.1 建立单局状态

现有 `BattleState` 只负责一场战斗。需要新增独立的 `RunState`，管理整局游戏：

```
RunState {
  runId,
  seed,
  currentFloor,
  currentNodeIndex,
```

#### 8.2 地图生成

固定每层战斗数：

| 楼层  | 非Boss战 | Boss | 商店   | Boss前火堆 |
| --- | ------ | ---- | ---- | ------- |
| 第一层 | 9      | 1    | 至少1间 | 固定1个    |
| 第二层 | 6      | 1    | 至少1间 | 固定1个    |
| 第三层 | 4      | 1    | 至少1间 | 固定1个    |

地图生成应分成两次处理：

首先生成固定战斗骨架，保证数量和顺序合法；然后按配置插入商店、火堆和特殊事件。

每层Boss前必须紧邻火堆，不允许其他节点插入中间。

#### 8.3 地图界面

建议用可点击的线性节点显示：

- 当前节点、已完成节点、后续节点。
- 普通战、精英战、Boss标识。
- 战斗属性类型和基准奖励。
- 商店、火堆、问号事件。
- 楼层进度和当前队伍信息。

尚未到达的节点可以查看信息，但不能跳过当前节点直接进入。

验收标准： 每局恰好经历22场战斗；精英计入战斗总数；特殊节点不改变战斗数量；Boss前必定有相邻火堆。

### 步骤9：实现战后奖励和角色招募

这里建议把“奖励候选生成”和“奖励界面”完全分开。

#### 9.1 卡牌奖励

建立统一的候选生成器，负责：

- 根据奖励来源确定合法卡池。
- 根据各卡持有数量上限过滤。
- 按稀有度和其他已定权重抽取。
- 同轮候选不能同名。
- 多轮之间允许重复出现同名卡。
- 不足3个合法候选时执行统一的待定处理策略。

| 来源        | 候选卡池         | 选择规则         |
| --------- | ------------ | ------------ |
| 普通战       | 已入队角色合并卡池    | 三选一，可跳过      |
| 精英战       | 已入队角色合并卡池    | 三选一，可跳过      |
| 第一、二层Boss | 已入队角色的稀有卡合并池 | 三选一，可跳过      |
| 招募        | 新招募角色的专属卡池   | 连续3轮，每轮必须选1张 |

战斗奖励不能把无色牌混入角色卡池。

#### 9.2 招募流程

第一、二层Boss成功结算后，队伍未满且有可招募角色时进入招募。

完整操作顺序：

Boss成功结算

完成本层奖励，包括稀有卡选择

随机展示最多3名未入队角色

玩家必须选择其中1名（若存在可招募角色）

获得该角色固定专属遗物

第1轮

3选1张卡

第2轮

3选1张卡

第3轮

3选1张卡

加入队伍，继续下一层

特别注意：Boss奖励选卡必须发生在招募之前，因此不能提前混入尚未加入队伍的新角色卡。

招募每轮重新检查持有上限，三轮结束共获得3张新角色专属卡。

验收标准： 可以从1人发展至最多3人；招募不会给角色建立独立战场坐标或独立血条；新角色的36种卡进入后续可获取池。

### 步骤10：实现火堆、商店和特殊事件

建议开发顺序为：火堆 → 商店 → 特殊事件。

火堆最简单，适合先验证地图节点切换。

#### 10.1 火堆

提供二选一：

1. 恢复最大生命值50%的生命量。
2. 升级一张未升级卡牌。

恢复量小数向上取整；普通治疗是否封顶应作为生命系统规则先明确。

不能同时获得恢复和升级，也不能在同一火堆重复操作。

#### 10.2 商店

按照策划案生成固定库存：

| 商品或服务 | 数量   |
| ----- | ---- |
| 角色卡   | 5    |
| 无色卡   | 2    |
| 通用遗物  | 3    |
| 付费删卡  | 每店1次 |
| 付费升级  | 每店1次 |

实现要求：

- 库存进入时生成，售出不补货。
- 价格生成后固定，不能靠重新进入刷新。
- 金币不足不能购买。
- 同店通用遗物不能重复。
- 已持有通用遗物不得再次出售或奖励。
- 删卡与升级分别拥有全局付费次数和各店独立次数。
- 下一商店恢复服务次数，但整局价格累计次数不清零。

卡牌、遗物价格的基础数值和服务涨价函数仍需确认后配置。

#### 10.3 特殊事件

建议先开发一个通用事件执行框架，而不是每新增事件就编写一套独立页面和逻辑。

单个事件配置可以包含：

```
事件ID
可出现楼层
生成权重
触发前提
显示内容
可选选项
各选项代价
各选项效果
随机判定配置
持续范围
```

第一批开发验证事件可以使用临时内容覆盖不同效果类型：

- 获得或失去金币。
- 直接失去或恢复生命。
- 删除、升级、复制一张卡。
- 获得无色卡。
- 获得适应属性。
- 改变后续战斗奖励基准。

这些是用于覆盖系统能力的开发测试事件，不是V15.7已经确定的正式事件名单。

验收标准： 同一个事件节点不能靠退出重进刷新；修改后续奖励时地图及时更新；属性不会突破楼层上限；特殊事件不能直接赠送通用遗物。

## 第四阶段：正式内容制作与平衡

### 步骤11：角色、卡牌和遗物内容

这是工作量较大的阶段，应在机制稳定之后批量开展。

V15.7要求每名角色拥有36种不同专属卡牌，围绕2～3种同等重要的核心机制设计，并拥有1件固定专属遗物。正式角色名单仍未定案。

游戏策划案_最终整合版_V15.7(3).md



#### 11.1 内容制作顺序

建议按以下顺序：

1. 先确定正式角色总数及首发角色名单。
2. 每名角色写明2～3个核心机制，以及如何与通用位移、击退、抽牌、消耗等机制联动。
3. 设计每名角色36种卡的普通版文字。
4. 为每一种卡确定升级版效果。
5. 配置稀有度、持有上限、目标规则、出牌条件、消耗标记。
6. 制作角色固定遗物。
7. 进行牌组循环与触发连锁的自动测试。
8. 再补充卡牌插画、音效和动画。

如果第一版先制作3名角色，就需要至少：

# 108

种专属卡

# 108

种升级版配置

# 3

件固定遗物

这是按3名角色计算的工作量示例，不代表正式首发角色数已经确定。

#### 11.2 遗物内容

建议把遗物开发分成三个验证批次：

| 批次  | 目的     | 功能覆盖          |
| --- | ------ | ------------- |
| 第一批 | 验证基础触发 | 出牌、抽牌、死亡、碰撞   |
| 第二批 | 验证复杂事件 | 快照、自动选目标、事件连锁 |
| 第三批 | 验证强力构筑 | 回收、次数限制、持续生效  |

正式通用遗物的稀有度分普通、罕见、稀有；第1层Boss奖励普通通用遗物，第2层Boss奖励罕见通用遗物，第3层Boss不提供遗物。

内容配置应当支持持续添加，而不要求程序员每次新增一件遗物都修改核心事件引擎。

### 步骤12：怪物、战斗组合和数值平衡

目前三种测试怪物可以继续用于开发测试，但不宜直接认定为正式内容。

#### 12.1 先建立战斗配置

每场战斗至少需要：

```
战斗ID
楼层编号
战斗类型
战场长度
玩家初始坐标
怪物类型与初始坐标
金币基准奖励
属性类型与基准点数
可用环境或特殊规则
```

第一阶段先把22场战斗的配置占位建立起来，确保完整流程可走通。

然后逐渐替换临时怪物组合、调整普通战和精英战的分布，并制作正式Boss。

#### 12.2 平衡测试维度

重点关注：

- 初始单角色能否完成第一层。
- 招募第二名角色后卡牌数量、抽牌效率是否明显变化。
- 三角色组合下是否产生异常强度。
- 左右包围局面是否存在可理解的应对方式。
- 怪物接触伤害是否使玩家过度依赖直接输出。
- Boss正常情况下是否有合理机会达到100%。
- 击退和无限连招是否显著改变Boss奖励效率。
- 天气与适应属性增长是否导致后期伤害失控。

注意，策划案明确允许玩家主动构筑可持续循环的无限抽牌和攻击组合。平衡不能通过偷偷限制每回合出牌次数或引入隐藏连锁上限解决；真正阻塞流程的自动触发闭环，应通过具体内容设计和测试消除。

### 步骤14：自动化验收和正式发布

现有验证记录应成为未来的回归测试基线，而不是被新测试替换。

第一层：规则单元测试

第二层：固定局面集成测试

复用现有测试战斗，新增天气、遗物连锁、Boss接触、复杂群体效果等专用测试局。

第三层：整局自动流程测试

用固定随机种子模拟一次完整局，从选角色开始，经过3层、22场战斗，最终成功或失败；检查不存在无法进入下一节点、重复领奖或错误存档的情况。

第四层：浏览器及Windows启动验收

继续验证拖牌、牌堆、响应式显示、场景切换、更新启动器以及本地修改保护行为。特别测试发布新版后 `.easysts` 缓存和存档不会发生非预期丢失。

## 六、实施时的统一验收原则

为了减少后续返工，我建议每个开发步骤都按同一个标准交付：

1. 规则完整： 已实现行为与V15.7对应章节一致，没有偷偷增加射程、能量、出牌限制等已取消机制。
2. 数据可配置： 新卡、敌人、遗物和奖励数值可以通过配置修改。
3. 可实际操作： 不能只通过单元测试，必须提供可在浏览器中进入的开发测试局面。
4. 可重复测试： 随机行为支持固定种子，能够重现问题。
5. 向后兼容： 原有战斗、卡牌拖拽、牌堆查看、界面和Windows启动器保持可用。
6. 有明确记录： 新增规则测试、浏览器验收结果和未解决问题同步更新项目文档。

## 七、优先级结论

现阶段最值得投入的不是增加更多卡牌插画或怪物种类，而是让基础战斗系统成为一个可以承载数百种卡牌效果和复杂遗物连锁的稳定引擎。

我建议接下来的实际开发顺序严格遵循：

事件队列与监听 → 统一伤害与群体结算 → 复杂击退 → 天气与属性 → 评分与Boss → 地图与奖励 → 招募 → 商店火堆事件 → 正式内容。

其中，第一项应当成为下一次 GitHub 开发任务的起点。它完成之后，后续绝大多数玩法都可以在原有系统上增加配置和界面，而不必反复重写战斗逻辑。

整个方案的目标是逐步把目前已能稳定完成单场战斗的《简单尖塔》，扩展成拥有3层22场战斗、可持续构筑、角色招募、天气成长、商店事件和独立Boss输出挑战的完整游戏。
